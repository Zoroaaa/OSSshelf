# OSSshelf 文件管理全链条现状分析与升级方案

> 日期：2026-11-09
> 范围：`apps/api`、`apps/web`、`packages/shared` 中与文件管理相关的链路，**明确排除 AI 模块**
> 性质：只做静态代码审计与方案设计，不修改业务代码、不提交
> 说明：文中行号基于 2026-11-09 当前工作区快照，后续重构可能偏移

---

## 0. 结论先行

### 0.1 五条关键判断

1. **主干能力已经具备，问题集中在“一致性”和“容量边界”**。多存储商抽象（自研 SigV4 + Telegram 适配）、分片上传、预签名直传、秒传去重、回收站、分享、WebDAV、权限解析都有真实实现，不是空壳；但配额、引用计数、路径、桶切换四处的记账规则互相矛盾，属于会“静默损坏数据/统计”的 P0 问题。
2. **最危险的不是缺功能，而是错误地删除共享对象**。去重引用计数设计为“原记录 +1、新记录从 1 开始”，两个逻辑文件会产生 3 个引用；删除新文件时引用计数为 1，会直接删除物理对象，导致原文件损坏（`apps/api/src/lib/dedup.ts:57-84`、`apps/api/src/routes/tasks.ts:1104-1132`）。
3. **配额与桶统计存在重复扣减**。单文件软删除已扣一次，永久删除/清空回收站再扣一次，定时清理再扣一次；恢复文件却完全不回补。`MAX(0, ...)` 会把负数悄悄抹平，掩盖问题（`apps/api/src/lib/fileService.ts:408-440`、`apps/api/src/routes/files.ts:1153`、`apps/api/src/routes/files.ts:1182`、`apps/api/src/routes/cron.ts:69-84`、`apps/api/src/lib/bucketResolver.ts:134-153`）。
4. **Worker 内存是整个传输链路的隐形上限**。ZIP 打包、URL 转存、WebDAV PUT、分享上传、在线编辑都走 `arrayBuffer()` 全量入内存；Workers 128MB 内存限制下，几百 MB 的文件就会失败，而接口声明的上限是 5GB。前端“fetch + blob”下载同样把整个文件放进浏览器内存。
5. **权限与审计“有表、有入口，但语义不完整”**。`accessLevel` 只写不读，属于声明了但未落地的能力；文件主链路（上传/下载/重命名/移动/分享访问）几乎不写审计日志，导致“文件日志”页面基本为空。

### 0.2 如果只做三件事

1. **重构配额与去重记账，并加对账任务**：统一“软删/永久删/定时清理/版本/恢复”的扣减规则，修正 refCount，给 `storageUsed` 与 `sum(files.size)` 做每日对账。这是唯一会直接造成用户数据丢失/容量失真的一组问题。
2. **给所有全量读内存的链路加上真正的流式或硬上限**：ZIP 流式化、下载支持 Range/直链、WebDAV PUT 大文件策略、分享上传分片化；否则大文件功能在真实网络下不可用。
3. **统一目录路径模型并给桶切换加护栏**：`path` 目前有两套写法，重命名文件夹不更新子项路径；修改文件夹桶只改元数据不迁移数据。建议统一为“parentId 为唯一事实，path 仅作缓存”，并在桶切换/删除前做阻断式校验。

## 2. 架构与数据模型速览

### 2.1 运行时

- 前端：React + Vite + Zustand（会话/界面状态）+ TanStack Query（服务端数据）；`Files.tsx` 是列表与上传编排的中心。
- 后端：Hono on Cloudflare Workers；D1（Drizzle ORM）；R2/D1/KV 绑定；对象存储通过自研 S3 客户端访问，另有 Telegram Bot 作为存储后端。
- 传输：小文件预签名 PUT；大文件预签名分片（10MB/片，并发 3）；Telegram 走 Worker 代理与 30MB 分片。

### 2.2 关键表

| 表 | 作用 | 关键事实 |
|---|---|---|
| `files` | 文件/文件夹统一存储 | `parent_id` 树 + `path` 冗余、`r2_key`、`hash` + `ref_count`、`bucket_id`（可空，表示继承）、`access_level`、`deleted_at`、`team_id` |
| `storage_buckets` | 多存储配置 | 加密后的凭据、`provider`、`is_default`、`is_active`、`storage_quota/used` |
| `upload_tasks` | 分片上传会话 | `status`、`r2_key`、`telegram` 分片信息、过期时间 |
| `download_tasks` | URL 转存任务 | 状态、进度、失败原因 |
| `file_permissions` | 授权 | `subject_type`（user/group/team）、`scope`（explicit/inherited）、`level`（read/write/admin）、`expires_at`、`inherit_to_children` |
| `shares` | 分享 | 密码（PBKDF2）、`expires_at`、`download_limit/count`、`is_upload_link`、上传限制 |
| `file_versions` | 版本 | 复用 r2Key、`version`、`size` |
| `audit_logs` | 审计 | `action`、`resource_type/id`、IP/UA、状态 |

### 2.3 三个基础约定（多处问题的根源）

1. **桶解析**：显式 `files.bucket_id` → 祖先文件夹最近的 `bucket_id`（递归 CTE）→ 用户默认桶（`apps/api/src/lib/bucketResolver.ts:40-115`）。每一步都可能“静默回退”，调用方很难感知实际落点。
2. **路径双轨**：普通接口写入 `${parentId}/${name}`（`apps/api/src/lib/fileService.ts:568`、`apps/api/src/routes/tasks.ts:1100`）；WebDAV 写入真实逻辑路径（`apps/api/src/routes/webdav.ts:638`）。WebDAV 读取时用两套策略兜底（`webdav.ts:374-441`）。重命名文件夹时只改自身路径（`fileService.ts:347-381`），子项路径立即失真。
3. **配额口径**：用户配额按“逻辑大小”累加（去重命中仍按完整大小计）；桶统计口径不统一——Telegram 分片完成路径按“物理增量”（命中时 +0，`apps/api/src/routes/tasks.ts:874-875`），S3/R2 分片完成路径按逻辑大小累加（`tasks.ts:1141-1143`）。删除/恢复/版本又各自采用不同口径，最终没有单一事实来源。

## 3. 链路逐一分析

### 3.1 多存储供应商接入与切换

**现在怎么做**

- 支持 R2、S3、OSS、COS、OBS、B2、MinIO、自定义 S3 与 Telegram；Provider 元数据集中在 `apps/api/src/routes/buckets.ts:27-37`。
- 凭据加密存储（`buckets.ts:263-265`），请求时解密为运行时配置。
- S3 客户端自实现 SigV4、path-style/virtual-hosted 判定、预签名、分片（`apps/api/src/lib/s3client.ts:55-189`、`191-268`、`270-441`）。
- 桶 CRUD、连通性测试、设为默认（`buckets.ts:290-313`）、启停（`buckets.ts:315-337`）、删除保护（`buckets.ts:395-441`）。
- 跨桶迁移是独立异步任务：逐文件读源写目标、改记录（`apps/api/src/routes/migrate.ts:341-520`）。

**真实瓶颈与设计债**

- **P0：切换默认桶不迁移存量数据**。只影响新上传的解析结果；已有文件继续按各自 `bucket_id` 读写，用户看到“换了存储但文件还在旧桶”，容量统计也对不上。
- **P0：修改文件夹的存储桶只同步文件夹元数据**（`apps/api/src/routes/files.ts:2261-2332`：更新目标文件夹与所有子文件夹的 `bucket_id`），既不迁移对象，也不改子文件的 `bucket_id`。子文件若 `bucket_id` 为空，会立刻解析到新桶，但 `r2_key` 仍在旧桶，表现为 404 或“文件消失”；子文件若已有显式 `bucket_id`，则继续留在旧桶，目录内出现“半迁移”状态。
- **P1：删除桶的保护不完整**。只检查显式 `bucket_id` 指向该桶的文件（`buckets.ts:410-428`）；`bucket_id` 为空、通过祖先/默认桶解析落到该桶的文件夹与历史数据不会被拦截。删除配置后这些对象在解析链上静默回退到其他桶，读取结果是 404 或错误内容。
- **P1：允许停用默认桶**（`buckets.ts:315-337`）。停用后新上传无可用默认桶，只能报错或回退，缺少阻断提示。
- **P1：桶容量展示有两套来源**。列表接口按当前 `files.bucket_id` 聚合（`buckets.ts:81-110`），而实际写入可能走祖先桶，展示与真实物理占用不一致；`__no_bucket__` 分组进一步放大误解。
- **P2：桶解析存在多级静默兜底**。显式桶 → 祖先桶 → 默认桶 → “任意一个活跃桶”（`bucketResolver.ts:99-117`），最后一级会让无默认桶的用户把文件写进意料之外的桶；同时每次请求都解密凭据，没有缓存；祖先桶查询未带 `userId` 条件（`bucketResolver.ts:93`），属于防御性缺口。
- **P2：迁移任务不可恢复/不可回滚**。`waitUntil` 逐文件执行，失败只记日志，没有断点、重试、回滚（`migrate.ts:341-520`）；大桶迁移期间用户仍在写入，缺少一致性快照策略。

### 3.2 上传（分片/断点/秒传/并发/大文件）

**现在怎么做**

- 前端阈值：>100MB 走分片，否则单次预签名 PUT（`apps/web/src/services/presignUpload.ts:44-50`、`127-146`）。
- 分片：10MB/片、并发 3、跳过已上传分片、支持 `taskId` 续传（`presignUpload.ts:250-460`）。
- 哈希：客户端 `arrayBuffer()` 后 SHA-256（`presignUpload.ts:204`、`825-833`），随完成请求上报；后端据此秒传（`apps/api/src/routes/tasks.ts:1102-1118`）。
- 后端分片接口：创建会话、预签名分片 URL、完成合并（`tasks.ts:225-314`、`1057-1097`）。
- Telegram：50MB 以上启用 30MB 分片（`apps/api/src/lib/telegramChunked.ts:17-20`）。
- 失败兜底：预签名 PUT 遇 CORS 时走后端代理上传（`presignUpload.ts:214-219`、`apps/api/src/routes/files.ts:504-720`）。

**真实瓶颈与设计债**

- **P0：去重引用计数错误**。命中时原记录 `ref_count + 1`，新记录 `finalRefCount = 1`（`dedup.ts:57-75`、`tasks.ts:1104-1132`）。两个逻辑文件 = 3 个引用；删除新文件直接触发物理删除，原文件损坏。`existingSize` 虽被返回但未使用（`dedup.ts:79-82`），也未校验大小，存在用小文件引用大对象、逻辑配额失真的空间。
- **P0：同名文件无冲突策略**。完成上传时直接插入新记录（`tasks.ts:1121-1139`），不检查同目录同名；重复上传会产生多份同名文件，WebDAV 按名查找只取第一条。
- **P1：配额只在创建任务时检查**（`tasks.ts:225`），完成阶段不再校验也不预占；并发/拖拽多文件可突破配额。
- **P1：小文件哈希读全文件进内存**（`presignUpload.ts:204`），接近 100MB 时会占用大量主线程内存与时间；大文件又在结束时重读一次计算哈希（`presignUpload.ts:451`）。
- **P1：多选上传无全局队列**。文件选择框对每个文件直接调用 `handleUpload`（`apps/web/src/pages/Files.tsx:1288-1291`），N 个文件会产生 N 条并发任务；而文件夹上传是串行（见下条），两种路径并发模型不一致。
- **P1：文件夹上传的多处缺陷**：目录已存在时异常被吞掉（`apps/web/src/hooks/useFolderUpload.ts:89-90`），`folderIdMap` 拿不到路径映射，后续子文件回退到当前目录（`useFolderUpload.ts:101`），层级错位；每上传一个文件就 `invalidateQueries(['files'])`（`useFolderUpload.ts:116`），每创建一个目录再刷新一次（`222`），N 个文件触发 N 次列表刷新。
- **P1：断点续传体验不完整**。刷新后必须重新选择本地文件才能续传（`apps/web/src/pages/Tasks.tsx:307-320`）；前端页面发起上传时并未携带 `taskId`，实际只有任务页能用续传。
- **P2：清理只 abort pending 的分片会话**（`apps/api/src/routes/cron.ts:116-133`），未完成但已写入对象的直传/代理上传、失败任务的历史对象没有孤儿回收。
- **P2：Telegram 限制不一致**。前端硬编码 500MB（`apps/web/src/hooks/useFileMutations.ts:17`），后端分片能力与全局 5GB 上限不一致，用户无法预期。

### 3.3 下载

**现在怎么做**

- 前端先取预签名下载 URL，统一 `fetch` 成 blob 后强制下载（`Files.tsx:652-660`）。
- 预签名失败时回退 `/api/files/:id/download?token=...`（`Files.tsx:661-668`），后端流式透传 S3 响应（`apps/api/src/routes/files.ts:214-303`）。
- Telegram 桶由后端代理读取后返回。

**真实瓶颈与设计债**

- **P0：前端全量 blob 下载**。多 GB 文件直接占满浏览器内存，Chrome 的 Blob 上限也会导致失败；无法断点、无进度、低端移动设备必然崩溃（`Files.tsx:640-660`）。
- **P1：回退下载把 Bearer token 放在 query**（`Files.tsx:663-664`），会进入访问日志、Referer、浏览器历史，属于凭据泄露面。
- **P1：`/download` 不支持 Range/If-None-Match**（`files.ts:214-303`），而预览流支持 Range，两者能力不一致；视频/大文件下载无法续传。
- **P1：Telegram 下载整包读入内存**（`apps/api/src/routes/share.ts:656`、`apps/api/src/routes/preview.ts:361-389`），文件越大越接近 Worker 内存上限。
- **P0：ZIP 全内存构建**。后端把每个文件读成 Buffer 再交给 `ZipBuilder` 一次性 finalize（`apps/api/src/routes/batch.ts:550-577`、`files.ts:349-408`），接口上限 500MB 高于 Workers 可用内存，实际大目录打包必然失败；前端 `JSZip.loadAsync(arrayBuffer)` 同样全量入内存（`apps/web/src/components/files/filepreview/ZipPreview.tsx:72`）。
- **P2：下载成功写通知但没有审计记录**（`files.ts:270-281`），无法回答“谁在什么时候下载了什么”。

### 3.4 在线预览

**现在怎么做**

- 预览流接口按类型分流，S3 路径支持 Range 与 206（`apps/api/src/routes/preview.ts:317-433`）；Telegram 路径整包读入后切片。
- 缩略图接口当前直接返回原图（`preview.ts:482-512`），没有真正缩放。
- `GET /api/files/:id/preview` 是另一条全量返回路径，带 `Cache-Control: public`（`apps/api/src/routes/files.ts:151-211`）。

**真实瓶颈与设计债**

- **P1：缩略图未实现**。网格/列表视图直接加载原图，且 access token 放在 query（`apps/web/src/components/files/items/GridItem.tsx:76`、`ListItem.tsx:88`），流量、内存、首屏与凭据泄露风险叠加；缩略图接口名字与行为不符（`preview.ts:482-512`）。
- **P1：两条预览入口语义重叠**。`/api/files/:id/preview` 与 `/api/preview/...` 能力不同（一个无 Range、一个支持 Range），前端容易选错；前者对私有文件设置 public 缓存（`files.ts:151-174`），部署在共享缓存/CDN 时存在越权缓存风险。
- **P1：大文件预览策略缺失**。PDF/Office/压缩包预览依赖浏览器全量加载（`ZipPreview.tsx:72`），没有大小阈值、分页加载或“下载后查看”的降级。
- **P2：Telegram 桶的 Range 是伪 Range**：先整包读入再 `slice`（`preview.ts:361-389`），只是响应正确，内存并未节省。

### 3.5 重命名/移动/复制/批量操作

**现在怎么做**

- 单文件/文件夹重命名、移动走 `PUT /api/files/:id`，服务层 `renameFile` / `moveFile`（`files.ts:1759-1799`、`apps/api/src/lib/fileService.ts:244-381`）。
- 批量删除/移动/重命名/永久删除/ZIP 在 `apps/api/src/routes/batch.ts`；批量上限 100，逐条处理并返回成功/失败列表。
- 复制仅 WebDAV 的 `COPY` 有实现（`webdav.ts:804-1028`），Web 端没有复制入口（`GridItem.tsx:183-213` 仅分享/版本/重命名/移动/下载/删除）。

**真实瓶颈与设计债**

- **P0：重命名文件夹不更新子项 path**（`fileService.ts:347-381`）。依赖路径前缀的 WebDAV 查找、回收站恢复、清理逻辑全部受影响。
- **P1：移动文件夹先全表扫描再逐条更新**（`fileService.ts:308-337`、`batch.ts:224-237`）。目录越大写放大越严重，接近 D1 单次请求的子请求/CPU 限制。
- **P1：跨桶检测有漏洞**。仅当源和目标都显式 `bucket_id` 时才判跨桶（`fileService.ts:278-285`、`batch.ts:168-185`），继承桶的文件可以“静默跨桶移动”，对象不会迁移。
- **P1：批量操作无事务/无回滚**。逐条执行，部分成功只返回汇总（`batch.ts:86-109`、`153-221`），前端没有失败明细重试；批量移动对文件夹同样触发多次全表扫描。
- **P2：复制能力缺失**。Web 端无法复制文件/文件夹，用户只能“下载再上传”；WebDAV COPY 也把文件内容整包读入内存（`webdav.ts:839-843`、`973-977`），大文件复制不可用；复制出的记录 `hash` 相同但 `refCount` 重新从 1 开始，进一步搅乱去重账本。
- **P2：看得到但改不了**。共享授予 `write` 的用户在列表里权限显示为 `null`（`files.ts:978-986`），前端无法判断能否重命名/移动，只能操作后吃 403。

### 3.6 回收站与恢复

**现在怎么做**

- 软删除写 `deleted_at`；单文件软删立即扣配额与桶统计（`fileService.ts:408-440`）；文件夹软删递归标记但不扣子项配额（`fileService.ts:388-406`）。
- 回收站列表服务端分页（`files.ts:1067-1091`），但把文件夹与其子项同时列出。
- 恢复直接清空 `deleted_at`，按路径前缀恢复子项（`fileService.ts:578-613`）。
- 永久删除/清空回收站（`files.ts:1106-1185`、`batch.ts:364-447`）；定时清理 30 天（`cron.ts:36-110`、`apps/api/src/lib/cleanup.ts:151-213`）。

**真实瓶颈与设计债**

- **P0：配额重复扣减**。单文件软删扣一次；永久删除/清空再扣一次（`files.ts:1153`、`files.ts:1182`）；定时清理再扣一次（`cron.ts:69-84`、`cleanup.ts:184-191`）。桶统计同样重复 `-1`。
- **P0：恢复不回补配额与桶统计**（`fileService.ts:578-613`）。用户“删除→恢复”一次，`storageUsed` 就永久少一份。
- **P0：定时清理有两套实现**。`lib/cleanup.ts` 与 `routes/cron.ts` 各自实现，已经分叉：前者直接 `s3Delete`（不处理去重引用），后者调用 `releaseFileRef`。生产环境走哪条取决于触发器，行为不可预期（`apps/api/src/index.ts` scheduled 与 `routes/cron.ts` 同时存在）。
- **P1：删除语义不统一**。单文件软删释放配额，文件夹软删不释放；用户界面无法解释“回收站是否占空间”。永久删除/清空又按子项逐个扣减，导致同一文件可能被扣多次。
- **P1：恢复依赖 path 前缀**（`fileService.ts:602-608`），文件夹重命名过的子项会漏恢复。
- **P1：回收站列表重复展示**。文件夹与其内部文件同时出现在列表（`files.ts:1082-1089`），恢复粒度与用户预期不一致；批量恢复缺失（`apps/web/src/pages/Trash.tsx` 仅单条操作）。
- **P2：软删不清理版本引用、Telegram 分片记录、FTS 索引**，长期积累孤儿。

### 3.7 分享链接（密码/有效期/权限/访问统计）

**现在怎么做**

- 创建分享：密码 PBKDF2（兼容旧明文常量时间比较）、有效期、下载次数上限（`apps/api/src/lib/shareService.ts:42-58`、`apps/api/src/routes/share.ts:104-144`）。
- 上传链接：独立 token、最大文件大小、MIME 白名单、最大上传次数（`shareService.ts:152-192`、`share.ts:357-404`）。
- 匿名访问：密码通过 query 传递（`share.ts:406-462`）；文件夹只返回一层；预览/流/下载/整包 ZIP 各自入口。
- 统计：只有 `downloadCount/downloadLimit`。

**真实瓶颈与设计债**

- **P0：分享访问完全没有日志**。只有累计下载次数，没有时间、IP、UA、来源、独立访客、字节数；无法做访问统计，也无法排查泄露。数据库没有 `share_access_logs` 一类表。
- **P1：密码走 query**（`share.ts:408`、`514`、`581`、`621` 等）。URL 会进入日志、Referer、浏览器历史；应改为 POST 换取短期会话 Cookie/token。
- **P1：上传链接全量读内存**。匿名上传同样 `arrayBuffer()`，`maxUploadSize` 的声明值与 Worker 实际能力脱节；没有分片/断点。
- **P1：过期即物理删除**。定时任务直接删分享记录（`cron.ts:162-177`），用户无法看到“已过期”的历史，也无法续期；删除/创建/访问均无审计。
- **P1：权限语义分散**。分享能力与 `file_permissions` 无交集：匿名访问者能做什么只由分享入口代码决定，没有统一的“只读/可下载/可上传”能力模型。
- **P2：文件夹分享逐层浏览的实现是“每层单独接口 + 每层密码参数”**（`share.ts:510-578`），体验与安全性都一般；没有防盗链、没有频率限制（除密码尝试）。

### 3.8 WebDAV

**现在怎么做**

- Basic Auth（邮箱 + 密码）每请求 PBKDF2 校验（`apps/api/src/routes/webdav.ts:60-118`）。
- 支持 OPTIONS/GET/HEAD/PUT/DELETE/MKCOL/PROPFIND/PROPPATCH/MOVE/COPY/LOCK/UNLOCK。
- PROPFIND 每次请求构建全量文件夹缓存（`webdav.ts:181-196`、`314-348`）；路径解析双策略（`374-441`）。
- PUT 全量 `arrayBuffer()`（`webdav.ts:483`）；DELETE 永久删除；LOCK 为无状态伪锁（`webdav.ts:1031-1100`）。

**真实瓶颈与设计债**

- **P0：GET 不支持 Range**（`webdav.ts:444-480`）。视频、断点续传、大文件读取体验差，部分客户端会直接超时。
- **P0：PUT 全量入内存**（`webdav.ts:483`）。超过 ~100MB 基本无法成功，与“企业网盘挂载”预期严重不符。
- **P0：DELETE 绕过回收站与引用计数**（`webdav.ts:703-758`）。直接删对象、扣配额，不处理去重共享对象，可能误删其他文件的数据；删除后不可恢复。
- **P1：PROPFIND 全量构建文件夹缓存**（`webdav.ts:181-196`）。文件夹越多，单次请求越慢；`Depth: infinity` 实际只返回直接子项（`webdav.ts:315-371`），与部分客户端预期不符。
- **P1：LOCK 是伪锁**。只返回 XML，不阻止并发写；Office/macOS 客户端可能因此产生覆盖冲突（`webdav.ts:1031-1100`）。
- **P1：认证方式只有账号密码，每请求一次 PBKDF2**。已有 API Key 体系但 WebDAV 未接入；多客户端高频 PROPFIND 会放大 CPU。
- **P2：MOVE 无同名冲突/权限/跨桶检查**（`webdav.ts:761-802`）；COPY 会复制物理对象，但 `hash` 复用、`refCount` 重置，去重账本进一步混乱（`webdav.ts:804-1028`）。
- **P2：上传不写版本、不写 FTS、不写审计、不执行目录 MIME 策略**，与 Web 上传行为不一致。

### 3.9 目录与文件权限

**现在怎么做**

- 权限主体：user/group/team；`scope` 区分 explicit/inherited；`expires_at` 生效过滤。
- 解析顺序：owner → 显式 user/group → 显式 team → 向上递归继承（`apps/api/src/lib/permissionResolver.ts:42-170`、`343-444`）；结果写 KV 缓存（`132-160`）。
- 授权时把权限展开写入子项，标记 `inherited`（`apps/api/src/lib/permissionService.ts:62-113`），同时查询时仍会向上递归兜底。
- 列表根目录把“被授权的文件”平铺加入结果（`files.ts:854-910`）。

**真实瓶颈与设计债**

- **P0：`accessLevel` 只写不读**。仅 `permissionService.setFolderAccessLevel` 写入（`permissionService.ts:120-161`），权限判定全程只使用 read/write/admin，`public_read/public_write/team` 没有任何执行分支。这是“声明了但未实现”的典型。
- **P1：继承双机制并存**。写入时展开 + 查询时递归；新文件是否继承取决于创建路径是否调用 `inheritParentPermissions`；父级撤权时展开出来的 `inherited` 记录是否同步清理，取决于撤销实现，容易出现“已撤权但仍可访问”的脏数据。
- **P1：继承解析是 O(深度 × 3) 条 SQL**。每层分别查 user/group/team（`permissionResolver.ts:343-444`），深目录首次访问很慢；KV 缓存 5 分钟且失效点分散，正确性与性能都难保证。
- **P2：权限缓存失效依赖 KV 前缀扫描**（`permissionResolver.ts:174-199`），单次 `list` 上限 1000，权限变更在超大目录下可能残留旧缓存。
- **P1：列表不能返回真实权限**。非 owner 的 `permissionsMap` 一律为 `null`（`files.ts:978-986`），前端无法正确置灰/隐藏操作，只能试错。
- **P1：过期/失效授权的展示未过滤**。根目录平铺的“被授权文件”查询未过滤 `expires_at`，用户会看到点进去 403 的条目。
- **P1：目录 MIME 策略只校验直接父目录**（`apps/api/src/lib/folderPolicy.ts:16-47`），祖先策略不继承；WebDAV PUT、URL 转存、在线编辑绕过该校验（调用点仅 `tasks.ts`、`files.ts` 上传、分享上传）。
- **P2：能力粒度不足**。`read` 同时意味着可下载、可分享、可预览，无法表达“仅预览/禁止下载/禁止转存”。

### 3.10 配额与用量

**现在怎么做**

- 用户级与桶级配额；上传前检查（`tasks.ts:225`、`files.ts:524-539`、`webdav.ts:581-592`）。
- 更新使用 `MAX(0, ...)` 原子加减（`apps/api/src/lib/bucketResolver.ts:124-155`）。
- 桶列表实时聚合 `files.bucket_id` 展示容量（`buckets.ts:81-110`）。

**真实瓶颈与设计债**

- **P0：没有单一事实来源**。用户配额按逻辑大小；桶统计在 Telegram 路径按物理增量（`tasks.ts:874-875`），在 S3/R2 分片完成路径又按逻辑大小（`tasks.ts:1141-1143`）；版本不进用户配额但删除版本时又扣配额（`apps/api/src/routes/versions.ts:306-360`），四处口径互相冲突。
- **P0：`MAX(0, ...)` 掩蔽负数漂移**（`bucketResolver.ts:134-153`），问题不会报错，只会越用越不准。
- **P1：只检查不预占**（`bucketResolver.ts:157-172`）。并发上传/转存可以同时通过检查，最终超额。
- **P1：没有团队/目录配额**，也没有 80%/95% 告警；前端只有粗略展示。
- **P1：没有例行对账**。后台有存储审计能力，但没有定时跑“用户 `storageUsed` vs `sum(files.size)`”“桶 `storageUsed` vs 实际对象”的对账与修复任务。

### 3.11 搜索与筛选

**现在怎么做**

- `/api/search`：默认名称 LIKE，可选 FTS5，语义/混合搜索依赖 AI 配置（AI 部分不在本方案范围）；支持 MIME、大小、时间、文件夹、标签、桶过滤，服务端排序分页（`apps/api/src/routes/search.ts:127-283`）。
- 前端提供高级筛选面板与搜索历史。

**真实瓶颈与设计债**

- **P0：FTS 零命中会返回全量文件**。`ftsIds.length === 0` 且 query 非空时不追加任何条件（`search.ts:154-181`），用户搜不到时反而看到整个网盘，属于明确的正确性缺陷。
- **P1：搜索范围仅本人文件**（`search.ts:127`）。被授权/团队文件不可全局搜索，与“共享文件夹”体验冲突。
- **P1：LIKE 未转义 `%`/`_`**（`search.ts:153`、`165`、`185`），与列表接口已转义的行为不一致，特殊字符会扩大匹配。
- **P1：前端双轨搜索**。文件名输入框在未触发服务端搜索时只过滤“当前页”（`Files.tsx:299-312`），用户会误以为全库搜索；标签搜索也在前端过滤当前页。
- **P2：语义结果可能生成超大 `IN` 列表**（`search.ts:167-168`），接近 D1 SQL 变量上限；没有截断/分页策略。

### 3.12 排序与分页

**现在怎么做**

- 后端支持 `sortBy`（createdAt/updatedAt/name/size）、`sortOrder`、`page/limit`，limit 上限 100（`files.ts:773-790`、`932-951`）。
- 前端默认每页 20，可切 50/100；`Pagination` 组件展示总数与跳页。

**真实瓶颈与设计债**

- **P0（体验级正确性）：排序只对当前页生效**。前端根本没有把 `sortBy/sortOrder` 传给列表接口，而是在 `displayFiles` 里对当前页排序（`Files.tsx:307-311`）。用户按名称/大小排序时，跨页顺序是错的。
- **P1：文件夹置顶只在页内可靠**。服务端排序没有统一的“文件夹优先”规则，跨页后顺序混乱。
- **P1：中文名称按二进制排序**。SQLite 默认 `BINARY`，没有拼音/自然排序（`file2` 会排在 `file10` 后面）。
- **P1：无虚拟滚动/无限加载**。100 条/页的网格在低端设备上渲染压力明显；每次翻页都整页 refetch。
- **P2：总数与列表两条查询**（`files.ts:960-1005`），大表下成本翻倍；无游标分页。

### 3.13 移动端体验

**现在怎么做**

- 移动端工具栏提供视图切换、排序、新建/上传入口（`apps/web/src/components/files/MobileFilesToolbar.tsx:49-119`）；网格/列表自适应。
- 移动端列表/网格每项都有独立的选择框与“更多”按钮，单元格点击进入预览或打开菜单（`apps/web/src/components/files/items/ListItem.tsx:61-129`、`items/GridItem.tsx:63-122`）；批量操作栏在选中后出现（`Files.tsx:1342-1350`）。
- 图片缩略图直接请求 `/api/files/:id/preview?token=...`（`GridItem.tsx:76`、`ListItem.tsx:88`）。

**真实瓶颈与设计债**

- **P1：移动端排序仍是页内排序**。与桌面同源，切换名称/大小排序只对当前页生效（`Files.tsx:307-311`、`MobileFilesToolbar.tsx:82-105`），翻页后顺序错乱。
- **P1：上传没有队列与后台保持**。多选文件时每个文件直接并发 `handleUpload`，文件夹上传串行且逐文件刷新（`Files.tsx:1288-1291`、`useFolderUpload.ts:116`）；移动端切后台/锁屏后容易中断，没有恢复入口。
- **P1：缩略图实为原图**。移动端网格/列表直接用 `/preview` 原图作为缩略图（`GridItem.tsx:76`、`ListItem.tsx:88`），图片目录首屏流量与内存压力大。
- **P1：下载/预览内存问题在移动端更严重**。`fetch + blob` 下载与全量 ZIP 预览在中低端机型上极易崩溃。
- **P2：触屏交互仍以“更多”小图标为主**。没有长按菜单；可补充长按/滑动操作，但当前不是阻断性问题。
- **P2：断点续传不可见**。移动端没有任务中心入口提示，用户不知道上传是否还能续。

### 3.14 错误与失败重试

**现在怎么做**

- Axios 统一 60s 超时；401 自动登出（`apps/web/src/services/api-client.ts:15-46`）。
- 上传任务页支持续传（`Tasks.tsx:207-208`、`314`）；下载任务支持重试/暂停/恢复（`Downloads.tsx:207-290`）。
- 批量操作返回 success/failed 汇总。

**真实瓶颈与设计债**

- **P1：没有统一错误码到用户文案的映射**，大量依赖后端 message；同一类错误在不同页面文案不一致。
- **P1：没有自动重试/指数退避**。网络抖动或 S3 5xx 直接失败；分片上传单点失败后需回任务页重新选文件，不能自动重试。
- **P1：失败队列不持久**。上传/下载失败后刷新页面即丢失，没有“失败箱”。
- **P1：批量操作无失败明细重试**。只弹“成功 N 失败 M”，用户无法知道哪些失败、为何失败。
- **P2：60s 全局超时不适合代理上传/大 ZIP**（`api-client.ts:15-18`），会误杀长任务。
- **P2：无弱网/离线状态提示**，上传中断后界面停留在“上传中”。

### 3.15 审计日志

**现在怎么做**

- `audit_logs` + `createAuditLog` 工具（`apps/api/src/lib/audit.ts:29-80`）。
- 管理端用户/团队/权限/批量操作/URL 转存等部分动作有记录；文件详情页提供 `/api/files/:id/logs`（`files.ts:1661-1714`）。

**真实瓶颈与设计债**

- **P0（能力缺口）：文件主链路基本无审计**。上传、下载、预览、重命名、移动、恢复、清空回收站、分享创建/访问、WebDAV 操作均不写日志；文件日志页因此几乎为空。
- **P1：分享访问无日志**，与 3.7 的访问统计缺失同源。
- **P1：资源维度不统一**。批量操作以 `resourceType='batch'` 记录，按文件 ID 查询查不到；同一文件的操作分散在不同资源类型下。
- **P2：没有保留策略、导出、告警**；审计表会无限增长，也无法满足合规取证。

## 4. 现有功能优化清单（按投入产出排序）

> 排序原则：先修“会坏数据/会误导用户”的 P0，再做“影响可用容量”的 P1，最后做体验与可维护性。工作量以熟悉代码库的 1 人计，单位为人天。

| # | 优先级 | 问题 | 改法 | 预期收益 | 工作量 | 风险 |
|---|---|---|---|---|---|---|
| 1 | P0 | 去重 refCount 记账错误，删除会误删共享对象 | 改为“以物理对象为单位的引用表”（object_refs）或统一 `refCount` 归口到持有对象的记录；上传命中不再给原记录 +1，而是新记录 refCount=0 且所有删除都走同一释放函数 | 消除数据丢失；秒传可信 | 2-3 | 需迁移存量 `ref_count`，必须写回填脚本 |
| 2 | P0 | 软删/永久删/定时清理重复扣配额，恢复不回补 | 规定“软删不扣、永久删扣一次”或“软删扣、恢复补”，二选一；把配额变更集中到单一 service；清理统一走该 service | 配额可信，客服工单显著减少 | 3-5 | 规则变更属产品决策；存量需对账修复 |
| 3 | P0 | 定时清理双实现且行为分叉 | 保留一个实现（建议 `lib/cleanup.ts`），`cron` 路由只做触发；统一走 `releaseFileRef` 与配额 service | 行为可预期，避免误删 | 1-2 | 需确认生产触发器实际路径 |
| 4 | P0 | FTS 零命中返回全量 | `ftsIds` 为空时显式 `where 1=0`（或回退 LIKE 并合并结果） | 修复明显错误搜索结果 | 0.5 | 低 |
| 5 | P0 | 重命名文件夹不更新子路径 | 统一“parentId 为事实来源”，`path` 改为派生/缓存；或在重命名时批量更新子孙（注意写放大） | WebDAV/恢复/清理恢复正常 | 2-3 | 双 path 历史数据需回填 |
| 6 | P0 | 文件夹换桶只改元数据，不迁移对象 | 禁止直接换桶或改为“创建迁移任务 + 完成后切换”；子文件同步处理 | 避免“文件消失” | 1-2（仅护栏）/ 5-8（含迁移） | 误操作不可逆，需二次确认 |

## 7. 建议落地顺序（分批，可独立上线验证）

### 批次 0：数据一致性（最高优先，先止血）

**范围**：去重引用计数、配额记账、回收站/永久删/定时清理统一、恢复回补、FTS 零命中、重命名子路径、桶切换/删除护栏。

**交付物**

- 统一 `quotaService`（唯一扣减/回补入口）与 `objectRefService`（唯一引用释放入口）。
- 数据回填脚本：重算 `files.ref_count`、`users.storage_used`、`storage_buckets.storage_used`。
- 后台对账任务：每日对比 `storageUsed` 与 `sum(files.size)`，输出差异报告（先只报告不自动修）。
- 上述 P0 修复 + 单元/集成测试。

**验收**

- 删除/恢复/永久删除/定时清理四类操作后，配额与桶统计与预期一致。
- 秒传两个文件后删除任意一个，另一个仍可下载。
- FTS 搜索无结果时返回空列表。
- 重命名文件夹后 WebDAV 可访问子文件。

**风险**：存量数据回填需可重复执行、可 dry-run；上线前备份 D1 与关键表。

### 批次 1：传输容量与可靠性

**范围**：流式 ZIP、下载直链/Range、WebDAV GET Range 与 PUT 限制、分享上传分片、上传队列/并发、同名策略、孤儿对象回收。

**交付物**

- 流式 ZIP 实现（或明确体积上限 + 分批下载）。
- 前端下载改为直链/短时 token，支持进度与大文件。
- 上传队列（并发 2-3、暂停/重试/失败箱）、文件夹上传复用同名目录并保持层级、批量结束后单次刷新。
- 上传完成阶段配额复检 + 预占。
- 清理任务覆盖孤儿对象（dry-run 报告先行）。

**验收**

- 1GB 文件夹 ZIP 在 Worker/浏览器均不 OOM（或按上限明确拒绝）。
- 1GB 文件上传/下载/断点续传可用。
- 100 个文件拖拽上传不产生 100 并发。
- CORS 预签名失败时自动回退代理且可完成。

### 批次 2：权限、分享与 WebDAV 能力

**范围**：`accessLevel` 落地或移除、`permissionsMap`、继承查询优化、分享访问日志与统计、分享密码改 POST/会话、WebDAV API Key/真 LOCK/删除进回收站。

**交付物**

- 权限能力矩阵与统一校验函数（Web/WebDAV/分享/直链）。
- 分享访问日志表、统计接口与分享详情面板。
- WebDAV 删除进回收站、Range、API Key、LOCK 语义说明（真锁或明确文档）。
- 审计覆盖补齐。

**验收**

- 权限矩阵用例全通过（owner/read/write/admin/过期/继承/团队）。
- 分享 PV/UV/下载量可查，且不泄露密码。
- WebDAV 删除后可恢复，视频可拖动。

### 批次 3：体验与移动端

**范围**：服务端排序、移动端多选/长按、批量进度与失败明细、上传中心 UI、回收站体验、缩略图降级。

**验收**

- 跨页排序正确；移动端可多选批量删除/移动。
- 批量操作可只重试失败项。
- 回收站保留期与占用空间提示清晰。

### 批次 4：新功能

**范围**：复制（含跨桶）、目录/团队配额、审计导出、直链增强、文件请求（可选）。

**验收**：每个功能独立开关/灰度，先小范围用户验证。

## 8. 如果只做三件事

1. **修好“配额 + 去重引用”这一套记账**（批次 0 的 #1-#3）。这是唯一会让用户文件损坏、容量越用越不准的问题，优先级高于任何新功能。
2. **把 ZIP/下载/WebDAV PUT/分享上传从“全量内存”改为“流式或明确硬上限”**。否则大文件能力只是接口声明，真实场景不可用，且会在 Workers 内存上限处随机失败。
3. **统一目录路径并给桶切换加护栏**（批次 0 的 #5-#6）。文件树是 WebDAV、恢复、清理、搜索的共同地基；地基不稳，后续每个功能都要打补丁。
